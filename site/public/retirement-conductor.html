The safe answer to “can we delete this column?”

Retirement Conductor turns a risky schema change into a verified campaign: it finds known consumers through DataHub, changes only an explicitly authorized Git/dbt target, validates with dbt, reconciles fresh evidence, and refuses the producer action until the declared evidence closes.

Built for data platform and analytics infrastructure teams that need more than lineage screenshots, deprecation flags, or owner acknowledgments.

Execute the reference proof

Retirement Conductor never interprets “nothing was returned” as “nothing depends on it.” If evidence is missing, stale, partial, ambiguous, contradictory, or natively unvalidated, retirement is refused.

01 / THE PRODUCT

From blast-radius report to enforceable change operation.

DataHub knows the cross-system graph. Git knows the source. dbt knows whether the changed model works. Retirement Conductor makes those authorities satisfy one continuously reconciled completion criterion.

Impact analysis stops at “these things may break.”

It can identify downstream assets, but it does not bind exact native identities, perform authorized changes, capture native validation, discover again, or stop the producer action.

Retirement Conductor owns the operational loop.

It freezes evidence scope, changes a reviewable target, accepts only valid receipts, reopens on drift, and returns a machine-enforceable decision from one canonical manifest.

A catalog deprecation flag records intent.

Flags, tickets, scores, acknowledgments, and successful API calls are context. None independently proves that a migrated consumer still behaves correctly.

The campaign records changed and validated state.

Every consumer is closed by a native validation receipt, verified removal, or proved non-applicability—or remains visibly blocking.

02 / CAMPAIGN LOOP

One field replacement. Seven controlled transitions.

The first supported vertical deliberately stays narrow: one warehouse column, one compatible replacement, one Git repository, native dbt validation, and DataHub as the context and reconciliation surface.

  1. 01Declare the exact legacy and replacement fields
  2. 02Resolve identities and inventory within a named envelope
  3. 03Freeze scope, fingerprints, policy, and target set
  4. 04Apply only the reviewed Git/dbt change
  5. 05Run dbt-native parse, build, and semantic tests
  6. 06Reconcile against fresh graph and source evidence
  7. 07Publish, verify, and permit or refuse the producer action
The result is bounded, not universal.

READY_TO_RETIRE means every consumer observed through the recorded sources has an acceptable disposition inside that fresh, completely paged evidence envelope. It never claims that invisible consumers cannot exist.

03 / ARCHITECTURE

A small deterministic control plane around existing authorities.

The system does not replace DataHub, Git, dbt, or the warehouse. It owns orchestration, durable campaign history, evidence contracts, refusal policy, and the final gate.

Evidence authorities

  • DataHub Core graph, schemas, ownership, lineage, and campaign document
  • Git commit, path, branch, and content fingerprints
  • dbt manifest, compiled model, build, and semantic tests
  • Native data-time and source-quality observations

Campaign engine

  • Pure deterministic four-way policy
  • Append-oriented SQLite event store
  • Versioned manifests, envelopes, receipts, and refusal codes
  • Exact authorization and source-precondition binding
  • Fresh reconciliation and one-time producer plan

Shared outputs

  • Canonical private campaign manifest
  • CLI inspect and explain views
  • Structurally redacted HTML report
  • Stable DataHub summary with verified read-back
  • Non-zero CI gate unless policy permits retirement

Authority stays where it belongs

DataHub remains the graph and shared-context system. Git remains authoritative for repository content. dbt remains authoritative for native validation. SQLite is the single-writer campaign transaction store. The producer workflow retains the destructive credential.

The model proposes; deterministic code decides

Model assistance may explain consumers or propose a minimal patch. It cannot decide identity uniqueness, authorization, preconditions, state transitions, receipt acceptance, or retirement readiness.

04 / POLICY

Refusal is a successful product outcome.

The policy produces exactly four decisions. Operator views, the DataHub summary, the HTML report, and the producer gate all consume the same canonical manifest instead of recomputing policy independently.

READY_TO_RETIRE

All required evidence is fresh and complete within scope, every consumer is acceptably closed, and reconciliation found no new consumer.

REVIEW_REQUIRED

Technical checks are sufficient, but a declared semantic or authority judgment still requires a responsible person.

BLOCKED

A required source, permission, identity, approval, validator, freshness bound, or pagination proof is unavailable or inconclusive.

UNSAFE

A known active, failed, stale, newly discovered, unresolved, or otherwise unacceptable consumer remains.

The gate exits zero only for READY_TO_RETIRE.

It rereads current state, validates provenance and digests, checks source and publication bindings, consumes one short-lived issued producer plan, and refuses replay. A prior green report or manifest is never reusable authorization.

05 / SUPPORTED SCOPE

Automation is intentionally narrow. Safety is not.

Git/dbt is the sole automated native mutation boundary. DataHub may reveal dashboards, notebooks, pipelines, charts, or models elsewhere; those consumers stay exact blockers until independent evidence closes them.

Inside the supported release

  • One field replaced by a compatible field in the same table
  • DataHub Core inventory, aspect reread, reconciliation, and publication
  • One explicit Git/dbt identity and reviewable one-file branch change
  • dbt parse, seed, build, tests, and source-level semantic parity
  • Single-writer SQLite state, deterministic replay, backup, and restore
  • CLI, public-safe report, durable summary, and producer refusal gate

Explicitly outside the claim

  • No Looker instance, adapter, schema, recipe, fixture, or release dependency
  • No automatic mutation of opaque non-repository consumers
  • No custom metadata graph, custom dbt compiler, or generic coding agent
  • No hosted multi-writer service or distributed scheduler
  • No production warehouse deletion during development acceptance
  • No universal safety, adoption, or customer-value claim from fixtures

08 / SAFETY MODEL

Every authority is narrower than the campaign.

Read, plan, apply, validate, reconcile, publish, and producer action are distinct capabilities. Authentication alone grants no mutation authority, and the campaign process never receives the producer’s destructive credential.

Before mutation

Resolve one exact native identity. Bind repository, branch, commit, file, content fingerprint, DataHub URN, dbt manifest node, policy, validator, target allowlist, approval, and expiry.

During validation

Copy the dbt project into bubblewrap with no host home, source checkout, or network namespace; constrain environment and resources; treat macros, hooks, packages, and generated content as untrusted.

At the producer gate

Reread sources and publication, verify canonical bindings, record intent before action, consume one issued plan, and refuse replay, drift, unavailable evidence, untrusted context, or a non-ready decision.

Campaign durability

Append-oriented SQLite events are authoritative over materialized cache. The store binds one resolved path and writer identity, refuses copied state and known shared filesystems, validates canonical replay before backup, and restores only to the original authority path.

Evidence hygiene

Secrets never enter specs, command arguments, manifests, public artifacts, or support packets. Raw source rows stay ignored. Public rendering structurally replaces sensitive identities before HTML generation rather than post-processing private output.

10 / FAILURE CONTRACT

Stable refusals make missing proof actionable.

Expected failures are domain results, not unexpected exceptions. The prefix identifies the failed authority and each result retains a safe next action without leaking sensitive content.

SPEC_Invalid or unsupported retirement intent
Identical fields, incompatible replacement type, unsupported cross-table mapping, or schema-invalid configuration refuses before any source mutation.
EVIDENCE_Unavailable, partial, stale, or unverifiable evidence
Incomplete lineage paging, missing required source, fixture-only proof, stale source time, or publication mismatch prevents readiness.
IDENTITY_Missing, ambiguous, or inconsistent native identity
Display names and aliases can assist discovery, but only one exact DataHub-to-native mapping can authorize apply.
AUTH_ / SCOPE_Mutation was not explicitly and exactly authorized
Plan mode, missing approval, missing or wrong plan confirmation, expired authority, a moved source, or any target expansion refuses before mutation.
VALIDATION_Source-native validation failed or was inconclusive
A successful apply or API response never closes a consumer. Only a passed native receipt bound to the exact target and artifacts can support VALIDATED.
RECONCILIATION_ / POLICY_Fresh evidence reopened or prevented closure
A late consumer, stale receipt, table-only edge, opaque external consumer, or disappearing edge without a valid closure remains visible and non-ready.
INTEGRITY_ / RUNTIME_State, provenance, or single-writer authority is not trustworthy
Digest mismatch, corrupt event chain, copied store, wrong writer, unsupported shared filesystem, unavailable trusted clock, or missing campaign state refuses rather than repairing itself into readiness.
GATE_The producer action cannot safely execute
Wrong run provenance, drifted state, unavailable DataHub, missing verified publication, expired or replayed plan, source change, or any non-ready decision exits non-zero without another action.

12 / HONEST LIMITS

What remains unproven.

The engineering vertical is complete. Adoption and production claims are deliberately not inferred from repository work.

Independent operation

RC-018 remains NOT_RUN. No independent prospective operator has yet established whether the workflow is operable without the author, recurrent, valuable, adoptable, or fundable.

Deployment boundary

Executed on Linux x86_64 with Python 3.11–3.14, local single-writer SQLite, DataHub Core 1.6.0, MCP 0.6.0, Git, dbt/DuckDB, Docker, and bubblewrap. macOS, Windows, musl, shared or multi-writer state, a product container, and DataHub Cloud remain unexecuted.

Evidence boundary

Official and generated data are still fixtures. Live-local integration proves the mechanics against disposable sources, not production graph completeness, production identity behavior, warehouse deletion, broad market demand, or universal safety.

Release provenance

The wheel and source archive reproduce byte-for-byte and carry checksums plus a runtime SBOM, but remain unsigned. SHA-256 detects changed content; it does not prove who produced the artifact.

Residual race

The producer plan is short-lived, one-time, and checked immediately before the local sentinel. A real separately privileged warehouse transaction still owns the final external race and must call the same gate inside its trusted invocation.
