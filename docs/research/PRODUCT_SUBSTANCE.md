# Product substance pass

## Question

After removing the pitch, report, and features DataHub already supplies, is
there still a valuable product that changes the world?

## Observed foundation

The prior live experiment did not merely render an impact graph:

- repository scope exposed one consumer;
- live DataHub scope exposed 35;
- DataHub added an external executive report through a real lineage path;
- the broader inventory reversed the completion decision;
- one source consumer was actually changed and passed dbt-native checks;
- unresolved external consumers prevented lifecycle mutation;
- the refusal state was written back and retrieved by another agent client.

The idea therefore starts with a demonstrated consequence, not only a
plausible problem.

## Subtraction tests

### Remove the visual interface

The product remains:

- a retirement specification;
- a campaign event log;
- source changes;
- native validator runs;
- reconciliation snapshots;
- a producer-side gate.

Conclusion: the interface is not the product.

### Remove generic model capabilities

The system can still discover, hash, authorize, invoke native tools, evaluate
policy, and refuse. Model assistance improves interpretation and patch
proposal quality, but it does not own the safety decision.

Conclusion: the idea is not generic agent packaging.

### Remove DataHub-native features

Subtract search, lineage, schemas, ownership, queries, deprecation metadata,
documents, and events. What remains is:

- evidence envelopes;
- cross-domain identity binding;
- native executor orchestration;
- source-version and target-scope guards;
- receipts and a common disposition model;
- fresh reconciliation;
- one producer-side completion gate.

Conclusion: a meaningful product remains after subtracting stock features.

### Remove DataHub itself

The Git/dbt migration can still run, but the demonstrated inventory collapses
from 35 known consumers to one repository consumer. Cross-platform scope,
ownership routing, graph reconciliation, and shared agent context disappear.

Conclusion: DataHub is a foundation for the current product claim, not a
decorative lookup.

### Replace the central noun

Changing “data field” to an arbitrary deployment or environment breaks the
workflow: consumer identity, graph evidence, native migration, and schema
semantics are domain-specific.

Conclusion: the pitch is not a generic readiness template with renamed nouns.

## Durable artifact test

The durable result is not a score. It is:

- changed consumer source or native content;
- source-native validation evidence;
- a reconciled campaign manifest;
- an enforceable gate result.

The manifest is secondary to the changed and validated state.

## Consequence test

The supported flow has four real consequences:

1. it creates a reviewable source change;
2. it runs the consumer's validator;
3. it can reopen on new graph evidence;
4. it can prevent the producing change.

If any of these are replaced by narrative or hand-authored status, the product
weakens materially.

## Value test

The product is valuable when:

- an asset has consumers outside one source repository;
- a breaking change requires more than notification;
- native validators exist but are fragmented across systems;
- the producing team needs an enforceable completion criterion;
- the cost of one missed consumer or prolonged manual coordination is high.

It is not valuable enough when a single repository and its native tests already
represent the complete consumer boundary.

## Falsifiers

Stop or reframe if:

- live DataHub evidence does not change action after realistic ingestion;
- the second adapter shares no useful lifecycle or receipt semantics;
- the native systems cannot provide source versions and validators strong
  enough for safe automation;
- the gate cannot be placed in the producer workflow;
- most target users accept ordinary tickets and do not need evidence-backed
  completion;
- a current product visibly executes and reconciles the same cross-system
  lifecycle.

## Conclusion

There is sufficient substance to build the complete product and test it in
operation. The thesis is strongest as cross-system completion and proof, not
as discovery, code generation, or governance alone.
